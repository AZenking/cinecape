## 一、已确认的流程边界

- 初始化与非初始化的分支只处理账号问题，不包含来源配置、内容导入等业务引导。
- 未初始化时，以弹窗让用户配置账号。
- 账号配置成功后可使用账号登录，登录后选择 Profile；不沿用此前建议的“配置成功后自动登录”。后续讨论已明确：登录与选档不是浏览公共页面的前置条件。
- 除设置页面外，所有页面均允许游客查看；游客可以查看所有内容，不采用此前助手建议的受限公开浏览范围。
- 只有登录后才能播放；播放使用所选 Profile 的权限进行校验。游客可浏览所有内容不表示可以匿名播放，也不表示取消登录后的 Profile 播放权限。
- 收藏的频道与点播观看历史按 Profile 区分；首页登录并选择 Profile 后展示该 Profile 的收藏频道和点播观看历史。
- 当前继续梳理首页，点播页面的具体设计暂不讨论；首页展示点播观看历史属于已确认范围。
- 主导航直接展示「首页」「点播」「直播」，右侧展示登录用户与当前 Profile。
- 点击主 Profile 后可选择「设置」，输入对应 PIN 验证通过后查看设置。
- 设置页面采用左侧子菜单、右侧菜单主体的布局。
- 直播页面上方展示正在直播的节目，其下展示即将播放的节目，再往下按类型展示正在直播的节目。
- 直播页面最上方提供「所有节目单」入口，点击进入 EPG 墙。

## 二、账号与主页面流程树

```text
打开应用
├── 未初始化
│   └── 弹窗：配置账号
│       └── 配置成功 → 使用账号登录
│           └── 选择 Profile → 进入主页面
│
└── 已初始化
    ├── 未登录 → 游客浏览所有公共内容
    │   └── 主动登录或点击播放 → 使用账号登录
    │       └── 选择 Profile → 展示个人内容，并可按权限播放
    └── 已有有效会话 → 恢复规则待明确

主页面
├── 顶部左侧菜单
│   ├── 首页
│   ├── 点播
│   └── 直播
└── 顶部右侧
    ├── 登录用户
    └── 当前 Profile
        └── 点击主 Profile
            └── 选择「设置」
                └── 输入对应 PIN
                    └── 验证通过 → 查看设置页面
```

「主 Profile」沿用用户本次描述，具体身份定义及其与账号管理权限的关系尚未确定。

上述账号分支只描述账号处理。已初始化但未登录时，用户可以直接以游客身份浏览，无需先经过登录页。公共浏览与播放的关系如下：

```text
公共浏览（除设置页面外，游客均可查看所有内容）
├── 首页
├── 点播及内容详情（页面设计暂不讨论）
└── 直播及所有节目单 / EPG 墙

点击播放
├── 游客 → 引导账号登录 → 选择 Profile
│   └── 继续原内容的播放流程（衔接建议，具体交互待明确）
└── 已登录并选择 Profile → 校验播放权限 → 播放

进入设置
└── 登录 → 主 Profile → 输入对应 PIN → 验证通过后进入
```

游客状态的顶部右侧展示及登录入口样式尚未确定。

## 八、前端架构调整方案（建议，尚未实施）

本节记录基于上述流程提出的架构方案。用户本次授权将方案补入文档，未授权修改业务代码；建议路由、模块划分和交互形式仍需在后续规格中落实，不代表已完成设计或实现。

### 8.1 调整原则与现状

核心调整是将「公开浏览」「登录后的个人内容与播放」「PIN 保护的设置」拆成三个边界。继续使用现有 React + TypeScript、Vite、React Router、HeroUI、Tailwind CSS 和播放器能力，无需更换技术栈。

当前前端以页面组件、业务组件和公共请求层组织：`App.tsx` 配置路由与守卫，`AppShell` 承载导航，`SessionProvider` 提供账号与当前 Profile，页面通过自定义 Fetch API 客户端请求服务端。列表、搜索、分页和表单主要保存在页面本地状态，播放生命周期由 `usePlaybackSession` 管理。

当前结构与目标流程的主要差异：

- `ProtectedPage` 将登录守卫与应用布局绑定，目录与详情也要求登录。
- 缺少独立的首页、点播页、直播页与 EPG 墙，媒体目前统一展示在目录中。
- 来源、档案、策略、设备等管理页面尚未统一到设置布局与设置 PIN 入口。
- 首页尚未形成按 Profile 展示收藏频道和点播观看历史的模块。

### 8.2 目标架构树

```text
应用入口
├── 初始化状态检查
│   └── 未初始化 → 弹窗配置账号
│       └── 配置成功 → 提供账号登录
├── 全局上下文（职责划分）
│   ├── Session：账号、登录状态
│   ├── Profile：当前观看档案
│   └── SettingsAccess：设置 PIN 解锁状态
└── 路由
    ├── 公共浏览布局
    │   ├── 顶部： 首页 / 点播 / 直播
    │   ├── 右侧：游客登录入口 / 登录用户与 Profile
    │   └── 页面主体
    │       ├── 首页
    │       ├── 点播（预留，本轮不设计）
    │       ├── 内容详情
    │       ├── 直播
    │       └── EPG 墙
    └── 设置布局
        └── 登录 + 主 Profile + PIN 校验
            ├── 左侧：设置子菜单
            └── 右侧：对应设置模块
```

### 8.3 路由与布局

拆开布局与访问守卫：公共布局负责导航和页面容器，不要求登录；权限守卫按设置入口或播放操作分别使用。

| 建议路由 | 职责 | 访问条件 |
| --- | --- | --- |
| `/` | 首页 | 游客可浏览 |
| `/vod` | 点播，预留入口 | 游客可浏览 |
| `/media/:id` | 内容详情 | 游客可浏览 |
| `/live` | 直播首页 | 游客可浏览 |
| `/live/guide` | EPG 墙 | 游客可浏览 |
| `/settings/*` | 设置及各子模块 | 登录、主 Profile、PIN 验证 |

初始化配置采用已确认的弹窗。登录和 Profile 选择建议也由统一弹层承载，以保留当前浏览语境；具体形式以及是否保留独立登录地址尚未确定。

### 8.4 会话、Profile 与设置解锁

| 状态 | 职责 |
| --- | --- |
| 登录会话 | 确定账号身份 |
| 当前 Profile | 确定收藏、历史归属与播放权限 |
| 设置解锁状态 | 确定当前是否允许进入设置 |

上述为逻辑职责划分，不要求立即拆成三个 Provider。现有 `SessionProvider` 可以继续承载服务端返回的账号和 Profile，无需立即引入新的状态管理库。

设置解锁单独管理，建议在切换 Profile、退出登录或解锁过期时失效。PIN 由服务端验证，前端负责输入与状态展示；有效期限、主 Profile 定义、未设 PIN 的建立流程及与敏感操作主账号密码校验的关系，仍需明确。

### 8.5 统一播放入口

首页、直播、详情以及后续点播页面应通过同一个播放入口发起操作，避免各页面重复编写登录与选档判断。

```text
点击播放
└── 统一播放协调层
    ├── 未登录 → 登录
    ├── 未选择 Profile → 选择 / 解锁 Profile
    └── 条件满足
        └── 服务端按当前 Profile 校验播放权限
            ├── 允许 → 现有播放器
            └── 拒绝 → 展示结果
```

建议保留原内容目标，登录和选档完成后继续播放流程。复用 `MediaPlayer`、`PlaybackControls` 和 `usePlaybackSession`；页面不直接处理播放票据、续期和心跳。

### 8.6 数据访问与隔离

```text
数据访问层
├── 公共浏览
│   ├── 内容目录、详情
│   ├── 直播分类
│   └── 节目单、EPG 墙
├── Profile 个人数据
│   ├── 收藏频道
│   └── 点播观看历史
├── 播放操作
│   └── 登录 + Profile 授权
└── 设置操作
    └── 管理权限 + 设置解锁及所需验证
```

公共目录请求不能继续强制依赖登录和当前 Profile。公共浏览接口返回可展示的元数据，播放地址与票据继续由受控播放接口提供；这一调整涉及前后端接口契约，不能只修改前端路由守卫。

收藏与历史的请求、状态和缓存均应以 Profile 为边界。切换 Profile 时立即清除旧展示、废弃旧在途请求，并重新加载对应数据，避免串档；可延续现有代次守卫机制。

### 8.7 页面与业务模块

- 首页：公共内容区，以及当前 Profile 的收藏频道和点播观看历史；公共模块与布局待讨论。
- 直播：所有节目单入口、正在直播、即将播放、按类型展示正在直播的节目。
- EPG 墙：建议由频道列表、时间轴和节目块组成；节目播放操作接入统一播放入口，其他交互待明确。
- 设置：统一承载第三节的候选子菜单，复用已有来源、档案、策略、设备业务组件。
- 点播：仅预留路由和导航，不展开页面设计。

建议逐步按业务模块收拢页面、请求与状态逻辑，避免继续堆入单个 `api.ts` 或大型页面组件：

```text
src/
├── app/                 路由、全局 Provider
├── layouts/             公共布局、设置布局
├── features/
│   ├── auth/            初始化、登录
│   ├── profiles/        档案选择、切换
│   ├── home/            首页
│   ├── live/            直播
│   ├── epg/             节目单
│   ├── favorites/       收藏
│   ├── history/         观看历史
│   ├── playback/        播放入口与播放器
│   └── settings/        设置模块
└── shared/              请求底座、通用 UI、工具
```

### 8.8 建议实施顺序与前置确认

1. 明确公共浏览、个人数据、播放和设置的接口与授权边界。
2. 拆分路由、公共布局与设置布局。
3. 接通统一登录、选档和播放入口，保留原播放目标。
4. 建设首页、直播与 EPG 墙，以及对应的 Profile 个人数据模块。
5. 随业务模块调整逐步整理目录，无需先做全仓目录重构。

优先继续确认主 Profile 定义、PIN 建立与解锁有效期，以及首页公共内容区。第七节待明确项仍然有效；本节没有将其视为已确定的实现要求。

## 九、后端调整范围（建议，尚未实施）

| 模块 | 当前情况 | 建议调整 |
| --- | --- | --- |
| 游客浏览 | 目录、详情、节目查询要求登录，并关联 Profile 策略 | 提供公共浏览能力，游客无需登录或选档即可查看全部内容 |

| 初始化与登录 | 已有初始化状态、创建账号和登录接口 | 基本复用现有能力，弹窗和页面衔接主要由前端处理 |

### 9.1 浏览与播放授权分离

当前 `CatalogController` 整体使用 `SessionGuard`，节目服务也沿用受保护的授权链。因此只移除前端登录守卫，无法让游客获得数据。目标后端接口分层如下：

```text
后端接口
├── 公共浏览：不要求登录
│   ├── 媒体目录与详情
│   ├── 直播分类、正在直播、即将播放
│   └── EPG 节目单
├── 个人数据：登录 + 当前 Profile
│   ├── 收藏频道
│   └── 点播观看历史
├── 播放：登录 + 当前 Profile + 播放权限
│   └── 解析、票据、流交付及播放控制
└── 设置：账号管理权限 + PIN 解锁
    └── 来源、Profile、策略、设备等管理操作
```

公共浏览提供标题、简介、节目时间等展示数据；播放源地址、文件路径和票据继续由受控播放链路管理。公共浏览的家庭资源上下文应由部署实例确定，不能依赖匿名客户端声明归属。现有「目录按 Profile 策略过滤」与新浏览要求的契约差异，需要在后续规格与接口设计中明确处理，不能直接以本记录替代原授权实现。

### 9.2 Profile 收藏与观看历史

收藏频道需要新增持久化数据与接口，以 Profile 为归属，服务端校验当前会话和档案归属。

现有设备播放记录接口要求主账号及当次密码，返回设备的播放会话和失败事件，不能直接作为首页个人观看历史接口。首页需要按当前 Profile 查询，并建议按媒体合并多次播放、按最近观看时间排序、关联媒体展示信息。

可以利用现有播放会话和心跳中的位置数据，但需独立设计历史数据维护与持久化，避免历史随临时播放会话的保留策略被清理。是否包含播放位置、跨设备续播、完成状态和删除记录，尚未确认，不作为已承诺范围。

### 9.3 直播聚合与 EPG 查询

- 批量获取频道及对应节目，避免前端逐频道请求。
- 按时间范围查询节目排期，支持 EPG 墙。
- 按类型组织正在直播的节目，支持频道分页或分批加载。
- 复用现有 EPG 导入、关联与手动匹配能力；节目类型来源、分类与排序规则仍待明确。

### 9.4 设置访问授权

复用现有 PIN 验证、错误计数和锁定能力，但为设置访问建立独立授权状态，建议绑定当前会话与主 Profile。当前选档解锁授予是一次性消费，不能直接当作持续的设置权限。

主 Profile 的定义、首次建立 PIN、解锁有效期与失效条件，以及是否替代现有管理操作的当次主账号密码验证，均需先明确。设置授权必须由服务端检查，不能只由前端隐藏入口实现。

### 9.5 契约、数据库与验证

收藏和个人历史至少涉及新增持久化结构与数据库迁移；设置解锁是否需要持久化，取决于最终授权方案。新增及变更接口需同步 OpenAPI、共享类型和相应测试。

后续实施应重点验证游客浏览、匿名播放拒绝、登录后按 Profile 播放授权、收藏与历史不串档、设置 PIN 校验及失效行为，并覆盖迁移与 PC 浏览器联调。

## 十、本轮仅做 PC 端

用户已明确：以上讨论的范围先做 PC 浏览器端。该范围覆盖相关前后端能力，不表示只改前端。

本轮包括：

- PC 公共布局、初始化账号弹窗、登录与 Profile 选择衔接。
- 游客浏览，登录选档后按权限播放。
- PC 首页，以及按 Profile 区分的收藏频道和点播观看历史。
- PC 直播首页与 EPG 墙，按鼠标、键盘交互估算。
- 设置页面、候选子模块整合及设置 PIN 授权。
- 所需后端接口、数据库迁移、契约与共享类型、必要测试和 PC 浏览器联调。

暂不包含：

- 手机端专门适配。
- TV 界面、遥控器操作与空间焦点导航。
- 原生客户端。
- 点播页面重新设计；仅保留其导航与路由规划，首页点播观看历史仍在本轮范围内。

具体 PC 浏览器兼容矩阵、分辨率与验收数据集待后续确定；此处不额外承诺全平台或全部硬件验收。
