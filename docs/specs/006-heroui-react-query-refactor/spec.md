## Clarifications

### Session 2026-10-27

- Q: 对于收藏星标、观看状态这类高频轻量操作，界面应该在服务端确认前就立即反馈成功（失败时自动回滚并提示），还是必须等服务端确认后才更新显示？ → A: 高频轻操作（收藏/星标、观看状态、进度类）采用乐观更新，失败自动回滚并提示；表单保存、PIN 验证与来源/策略等管理变更等待服务端确认后更新（选项 A）。
- Q: 哪些页面允许"再次进入时先显示缓存旧数据、再后台刷新"，设置类页面是否必须每次进入都请求最新数据？ → A: 浏览型内容（媒体目录、详情、EPG 指南、直播、收藏、历史）允许缓存即时显示+后台刷新；设置类数据（账号、档案、策略、来源、设备、EPG 配置）每次进入必须请求最新数据并以加载态呈现（选项 A）。
- Q: 引入统一组件库与数据查询库会增加浏览器需要下载的代码体积，是否要设定一个硬性的首屏加载预算（例如首屏传输体积增幅不超过 15%），用于验收时客观判定？ → A: 设硬预算——首屏关键路径传输体积增幅 ≤ 15%，组件库与查询库按需引入，超出即验收不通过（选项 B）。
- Q: 可交互控件全部更换后，键盘操作与读屏等无障碍能力的验收基线是什么——保持与调整前等价并依赖组件库默认无障碍能力，还是要追加全站 WCAG AA 级别的专项审计？ → A: 等价基线——键盘可达性、焦点管理与读屏标签不劣于调整前，并随组件库获得默认无障碍能力；全站 WCAG AA 专项审计不在本次范围（选项 A）。

### User Story 1 - 全站交互控件统一为组件库，清除原生控件 (Priority: P1)

作为 PC 端观看者/管理者，我在任何页面操作时，所见到的按钮、下拉选择、输入框、开关、
模态弹窗、提示确认、加载指示与错误提示，都来自同一套统一的组件库外观与交互习惯；
不再遇到"某些页面是浏览器原生灰色下拉框、另一些页面是样式化控件"的割裂体验。
当前设置（账号/设备/EPG/常规/策略/档案/来源）与 EPG 指南页面存在原生下拉框，
档案变更提示使用浏览器原生弹窗，均替换为统一组件库等价组件。

**Why this priority**: 这是宪法 v1.3.0 技术约束第 5 条的硬性合规要求（PC 端组件
必须基于 HeroUI、严禁原生交互控件），也是用户可直接感知的最高频体验差异；
且不依赖数据层调整，可独立先行交付。

**Independent Test**: 逐页操作全部 PC 页面并用自动化扫描检查，全部可交互控件均
渲染为组件库组件；原生 `<select>`、原生弹窗调用数量为 0，既有选项与提交行为不丢失。

**Acceptance Scenarios**:

1. **Given** 管理者打开设置来源页，**When** 展开"媒体来源类型"下拉，**Then**
   呈现组件库下拉选择器（支持键盘导航与搜索性为组件库默认能力），选项集合与
   当前选中值与调整前完全一致。
2. **Given** 观看者打开 EPG 指南页，**When** 切换日期与频道筛选，**Then**
   日期/频道选择控件为组件库组件，筛选行为与调整前一致。
3. **Given** 管理者在设置中触发档案主档变更提示，**When** 提示出现，**Then**
   提示为组件库对话框/提示组件（含确认动作），不再出现浏览器原生弹窗，且提示文案不变。
4. **Given** 对全部 PC 页面执行自动化扫描，**When** 检索原生交互控件标签与原生弹窗调用，
   **Then** 结果为 0 处。

### User Story 2 - 数据请求统一：一致的加载、错误、缓存与刷新体验 (Priority: P2)

作为 PC 端观看者/管理者，我在所有页面获得一致的数据加载体验：首次进入显示骨架/指示器；
请求失败时看到统一的可重试错误提示（含服务端问题详情的人性化文案）而不是白屏或卡死；
在近期看过的页面之间来回切换时，内容立即呈现并自动在后台更新，无需每次等待或手动刷新；
执行变更操作（收藏、进度、设置保存、PIN 验证等）后，相关页面数据自动更新，无需整页刷新。

**Why this priority**: 统一数据层是本次架构调整的核心价值（可维护性、行为一致性、
减少重复代码），直接决定后续每个功能页面的开发效率与体验下限；依赖 US1 之后的
组件统一基础（加载/错误态组件），故排在 P2。

**Independent Test**: 在慢网/断网/恢复网络的模拟下走查全部数据页面，三态呈现、
缓存即时显示、后台静默刷新、失败重试、变更后自动更新全部按统一规则工作。

**Acceptance Scenarios**:

1. **Given** 首次打开媒体目录页，**When** 数据尚在请求中，**Then** 页面呈现与最终
   内容布局对应的加载骨架（而非空白或整页转圈）。
2. **Given** 目录/指南页已加载过数据，**When** 离开后再次进入，**Then** 立即呈现
   上次数据，同时后台刷新；刷新完成后数据无缝更新，无布局跳动。
3. **Given** 请求失败（网络断开或服务端错误），**When** 页面渲染完成，**Then**
   呈现统一错误态与"重试"动作；重试成功后恢复正常展示；错误文案来自服务端
   问题详情（问题类型、状态码、稳定错误码）的人性化映射。
4. **Given** 用户在详情页收藏了影片，**When** 返回收藏夹页，**Then** 收藏夹已包含
   该影片，无需手动刷新页面。
5. **Given** 快速连续切换 EPG 日期或频道筛选，**When** 多个请求并发返回，**Then**
   界面只呈现与当前筛选匹配的最新结果，不出现旧结果覆盖新结果的闪烁。
6. **Given** 同一页面数据已在有效期内，**When** 用户在多个页面间共享同一份数据
   （如同一频道在指南页与播放页），**Then** 不发出重复请求，共享同一份缓存。

### User Story 3 - 个人数据缓存与身份严格隔离（安全底线） (Priority: P2)

作为 PC 端观看者，我在切换档案或退出登录后，任何页面（含缓存）都不再显示上一身份的
收藏、历史、进度或个人设置；作为游客，我浏览的公开页面不会混入任何个人数据。

**Why this priority**: 宪法原则二（Household/Account/Profile 隔离）与原则三
（公开浏览边界）的硬性要求；引入统一缓存层后，若缓存不清空，个人数据跨身份泄漏
的风险反而升高，因此与 US2 同级强制交付，作为 US2 验收的一部分联合测试。

**Independent Test**: 登录后产生收藏/历史/进度，切换档案或退出登录，逐页检查与
检查内存缓存，均无上一身份数据；旧在途请求返回后被丢弃。

**Acceptance Scenarios**:

1. **Given** 档案 A 已产生收藏与观看历史，**When** 切换到档案 B（或游客态），**Then**
   收藏夹、历史、继续观看等位置不显示档案 A 的任何数据。
2. **Given** 切换档案瞬间存在在途的个人数据请求，**When** 该请求返回，**Then**
   其结果被丢弃，不得写入界面或缓存。
3. **Given** 用户退出登录，**When** 重新以档案 C 登录，**Then** 全部个人数据页面
   仅显示档案 C 的数据；公共浏览内容照常可用。
4. **Given** 会话过期（服务端返回未认证），**When** 任一个人请求失败，**Then**
   统一引导重新登录，个人缓存被清空，不存在半失效状态下的个人数据展示。

### User Story 4 - 公共逻辑沉淀为共享 Hooks，优先复用成熟库 (Priority: P3)

作为前端维护者，我开发或调整页面时，通用逻辑（数据访问、防抖/节流、轮询刷新、
媒体查询、本地持久化、事件监听等）直接使用统一的共享 hooks 与经维护的成熟开源
hook 库，而不是在各页面复制粘贴相似实现；需要新能力时，先找现成库，确无合适实现
才自研，且自研集中在统一目录并有测试。

**Why this priority**: 这是"尽量少实现"的工程效率目标，价值长期但依赖前两个
故事的落地（数据访问 hooks 建立在统一数据层之上），故列为 P3。

**Independent Test**: 清点通用逻辑的重复实现数量与来源（库/自研），重复实现较
调整前下降；自研实现全部集中在统一目录且单测通过。

**Acceptance Scenarios**:

1. **Given** 页面需要"窗口宽度变化时切换布局"，**When** 开发者接入该能力，**Then**
   直接使用统一的共享 hooks（而非页面内各自监听 resize），全站行为一致。
2. **Given** 某通用能力存在成熟开源实现，**When** 评估是否自研，**Then** 优先采用
   开源实现；自研仅在开源方案无法满足时发生，且理由记录于计划文档。
3. **Given** 评审共享 hooks 目录，**When** 清点实现来源，**Then** 每个自研 hook
   均有用途说明与单元测试，无页面私有的重复通用逻辑。

### Edge Cases

- 首次加载即失败（无缓存可显示）：统一错误态 + 重试，不出现空白页面。
- 后台刷新失败但有旧数据（限允许缓存即时展示的浏览型页面）：保留旧数据展示并
  给出轻量提示（如"数据可能不是最新"），不用错误页替换已展示内容；设置类页面
  按 FR-012 每次请求最新，失败呈现统一错误态。
- 快速切换筛选/页面造成请求竞态：仅最新请求结果生效，过期响应被丢弃（含数据层
  自动取消在途请求）。
- 重复触发变更操作（双击保存/收藏）：操作去重或按钮禁用，不产生重复副作用；
  幂等语义保持（宪法技术约束 3）。
- 乐观更新失败回滚：轻操作乐观更新被服务端拒绝或网络失败时，界面自动恢复
  原状态并给出统一提示，不残留与服务端不一致的展示状态。
- 会话在浏览中途过期：个人查询统一失败处理 → 引导登录；公共浏览不中断。
- PIN 解锁/敏感操作再验证过程中：解锁事实与个人缓存不因组件替换或缓存引入而
  改变既有授权边界（宪法原则六：服务端再验证为准）。
- EPG 大窗口数据（多日期 × 多频道）：按键控缓存隔离，切换日期/频道不互相覆盖；
  窗口过期语义（如服务端返回日期过期错误）按既有契约处理并允许恢复。
- 组件库组件与既有自动化测试断言的兼容：替换原生控件后，测试选择器/断言同步更新，
  E2E 全部通过。

## Requirements *(mandatory)*

### Functional Requirements

**范围与选型约束**（用户与宪法明确指定，作为需求约束而非实现细节）：

- **FR-000**: 本特性范围限于 PC 端 Web 呈现层；统一组件库必须采用 HeroUI
  （宪法 v1.3.0 技术约束第 5 条），服务端数据请求必须采用 react-query
  （用户指定）；通用逻辑必须优先采用经维护的成熟开源 hooks 库，尽量少自研
  （用户指定）。具体 hook 库选型与缓存策略在计划阶段调研确定并经 ADR 记录。

**UI 组件统一（对应 US1）**：

- **FR-001**: PC 端全部页面的可交互控件（按钮、输入框、下拉与选择器、开关、
  日期/时间选择、模态框与对话框、提示与确认、加载与进度指示、表格、标签页、
  菜单、导航）必须渲染为统一组件库（HeroUI）组件。
- **FR-002**: 浏览器原生交互控件（原生 `<select>`、`<datalist>`、
  `<input type="date|time|file">`、`<dialog>`、`<progress>`/`<meter>` 及
  `alert()`/`confirm()`/`prompt()` 调用）在全站源码中的数量必须为 0；
  现存 7 处原生下拉与 1 处原生提示必须替换为组件库等价组件。
- **FR-003**: 组件替换不得丢失既有能力：选项集合、当前值、变更回调、提示文案、
  校验规则必须与调整前等价。无障碍验收基线为"不劣于调整前 + 组件库默认无障碍
  能力"（键盘导航、焦点管理、读屏标签随组件库获得）；全站 WCAG AA 专项审计
  不在本次范围。
- **FR-004**: 页面视觉风格必须来自组件库统一主题体系；禁止为绕开组件库而逐页
  手写控件样式；确需偏离默认外观时必须经由主题令牌/变体实现。

**数据请求统一（对应 US2）**：

- **FR-010**: 全部服务端数据读取必须经过统一查询/缓存层（react-query）；
  组件不得各自维护"加载中/已加载/失败"的手写状态机（当前设置各页面 9–24 个
  手写状态的做法必须消除）。
- **FR-011**: 数据加载必须呈现统一三态：加载态（骨架/指示器，与内容布局对应）、
  错误态（统一文案 + 重试动作）、成功态；三态呈现组件全站复用。
- **FR-012**: 缓存必须提供"立即展示旧数据 + 后台静默刷新 + 无缝更新"的行为；
  再次访问近期已加载内容时不得出现阻塞性整页加载。适用范围分档：浏览型内容
  （媒体目录、详情、EPG 指南、直播、收藏、历史）允许缓存即时显示；设置类数据
  （账号、档案、策略、来源、设备、EPG 配置）每次进入必须请求最新数据并以
  加载态呈现，不得以缓存旧值先行展示。
- **FR-013**: 全部变更操作（收藏/取消收藏、进度上报、观看状态、设置保存、
  PIN 验证、档案与来源管理等）必须经统一变更层执行；成功后相关查询必须自动
  失效或更新，界面无需整页刷新。反馈语义分档：收藏/星标、观看状态、进度类
  高频轻操作采用乐观更新（先更新界面，失败自动回滚并以统一提示告知）；
  表单保存、PIN 验证与来源/策略等管理类变更等待服务端确认后更新。
- **FR-014**: 变更操作必须保持幂等语义（宪法技术约束 3）与既有服务端契约
  （请求路径、凭据档位、问题详情错误映射）不变；后端接口不得因本次调整而变更。
- **FR-015**: 请求取消必须自动化：页面卸载、筛选参数变化时，在途请求被取消或其
  结果被丢弃，过期响应不得回写界面（宪法原则二"阻止旧在途响应回写"的呈现层落实）。
- **FR-016**: 凭据档位必须保留并区分：公共（匿名、身份无关）请求与个人/设置
  （会话）请求分域管理；公共缓存与个人缓存必须隔离，公共响应不得进入个人缓存域。
- **FR-017**: 401/403/404/409/423/429 及稳定错误码的既有处理路径必须保留，
  并在统一数据层集中实现；未认证错误统一触发重新登录引导。
- **FR-018**: 遗留数据访问入口（`lib/api.ts`）必须迁移至统一查询层后删除，
  不得与统一层双轨并存；统一 fetch 底座保留为数据层唯一传输底座。

**身份隔离（对应 US3，安全底线）**：

- **FR-020**: 切换档案、退出登录、会话失效时，必须清空全部个人数据缓存并
  中止在途个人请求；清空后任何页面不得残留上一身份的收藏、历史、进度、个人设置。
- **FR-021**: 个人数据的查询与变更必须以经验证的当前身份为键控；不得仅以
  资源路径作为缓存键而忽略身份上下文。
- **FR-022**: 游客可浏览的公共页面照常工作，不因登录态变化而出现缓存污染；
  登录前后公共内容的缓存键与公共域隔离策略由 ADR 明确并经验证。

**共享 Hooks 与少自研（对应 US4）**：

- **FR-030**: 通用逻辑（数据访问、防抖/节流、轮询、媒体查询、元素尺寸/焦点/
  键盘监听、本地存储持久化等，按实际需要）必须优先复用成熟开源 hooks 库；
  选型必须在计划阶段对比后确定（评估维护活跃度、体积、与现有栈兼容性）。
- **FR-031**: 确无现成库能力时才允许自研 hook；自研 hook 必须集中在统一目录、
  附用途说明与单元测试，并优先基于开源库能力组合而非从零实现。
- **FR-032**: 既有分散的页面级通用逻辑（如各页面的加载/错误处理、设置页媒体
  查询、EPG 窗口计算中的通用部分）必须迁移至共享 hooks 或开源库，消除页面间
  复制粘贴的重复实现。
- **FR-033**: 每处新增手写基础设施（封装、hook、工具）必须在计划文档中记录
  "为何不采用现成库"的理由；无法给出理由的自研必须改为复用库。

**质量与回归（宪法原则一）**：

- **FR-040**: 调整过程中全部既有用户可见能力不得回退：初始化/登录、档案选择与
  PIN、公开浏览、媒体目录与详情、EPG 指南、直播、播放与进度、收藏、历史、设置
  全模块回归通过。
- **FR-041**: 既有自动化测试必须全部通过或随行为等价替换同步更新；替换原生控件
  后的端到端测试不得依赖实现细节脆弱断言；并新增负向验收用例（跨档案缓存泄漏
  检测、未认证请求拒绝、过期响应不回写）。
- **FR-042**: 静态类型检查、代码规范检查、单元/集成/端到端测试必须在每次增量
  合入前全部通过（合并前质量门禁）。
- **FR-043**: 领域核心与共享包不得反向依赖任何 UI 框架或查询库（宪法技术约束 4）；
  查询层与组件库仅存在于呈现层应用内。

### Key Entities *(include if feature involves data)*

- **查询条目（Query Entry）**: 按"资源 + 参数 + 身份域"键控的服务端数据缓存单位；
  携带新鲜度状态（新/过期）与刷新时机；公共域与个人域分开管理。
- **变更条目（Mutation Entry）**: 一次有副作用的服务端操作；携带幂等键（按契约）、
  执行状态，以及成功后需要失效/更新的相关查询集合。
- **身份缓存域（Identity Cache Scope）**: 公共（匿名）与个人（Profile）缓存的
  隔离边界；身份切换时个人域整体丢弃。
- **共享控件与 Hooks 清单**: 统一组件库组件用法与共享 hooks 的注册清单
  （名称、用途、来源：开源库/自研），作为评审与后续开发的唯一参考入口。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 自动化扫描全站 PC 页面源码与渲染结果，浏览器原生交互控件与原生
  弹窗调用数量为 0；统一组件库组件覆盖率 100%。
- **SC-002**: 手写"加载/错误"状态机与重复数据访问代码相比调整前减少 ≥ 60%
  （以各页面加载/错误相关状态代码处数统计）；数据访问入口唯一（遗留封装删除）。
- **SC-003**: 再次访问近期浏览过的页面时内容立即呈现（无可感知阻塞加载），
  后台刷新在 1 个网络往返内完成且无布局跳动。
- **SC-004**: 模拟任一页面网络失败 100% 出现统一错误态与重试入口；无白屏、
  无未处理异常、无错误信息泄漏内部细节。
- **SC-005**: 切换档案/退出登录后，全部页面 100% 不出现上一身份的个人数据
  （负向安全用例通过，含在途请求丢弃验证）。
- **SC-006**: 通用逻辑重复实现较调整前减少 ≥ 50%；自研基础设施新增为 0，
  或每处均有书面"为何不采用现成库"的理由；选用的开源 hook 库均有活跃维护
  （近 12 个月内有发布）。
- **SC-007**: 全部既有端到端流程（初始化→登录→选档→浏览→播放→收藏/历史→设置）
  回归通过率 100%，含新增负向用例。
- **SC-008**: 新增一个只读数据展示页所需的数据接入样板代码较调整前显著减少
  （评审时可对照演示：只写"查询定义 + 组件渲染"即可获得加载/错误/缓存能力）。
- **SC-009**: 生产构建下首屏关键路径传输体积较调整前增幅 ≤ 15%；统一组件库与
  查询库按需引入（以构建产物体积测量，超出即验收不通过）。

## Assumptions

- **范围边界**：仅 PC 端 Web 应用（`apps/web`）；服务端接口契约、`@hmp/shared`
  类型与数据库不做变更。移动端/其他终端不在本次范围（宪法 v1.3.0 约束为 PC 端）。
- **选型既定**：HeroUI 与 react-query 为用户与宪法明确指定，不作为开放问题；
  具体 react-query 缓存策略（键控、新鲜度时长、重试策略）与开源 hooks 库选型
  （候选方向：ahooks、react-use、usehooks-ts 等成熟库）在计划阶段调研并经 ADR 确定。
- **行为保持**：本次为等价重构，不新增/删除用户功能；URL 路由结构不变；
  视觉允许随组件库主题统一发生合理变化，但信息架构与操作流程不变。
- **增量交付**：按用户故事分阶段增量迁移，每个阶段独立可验证、可合入；
  不采用一次性全量切换后统一验证的方式。
- **依赖现状**：HeroUI 3.2.6 已在依赖中声明但尚未使用；现有统一 fetch 底座
  （含问题详情错误映射与取消语义）保留为传输底座，在其上建设查询层。
- **身份边界不变**：PIN、设置解锁、敏感操作再验证等既有授权机制的行为与
  服务端校验不变（宪法原则六）；本次仅呈现层实现方式调整。

## 宪法合规评估

- **原则一（规格驱动与多层证据验收）**：本规格为 Proposed，接受前不得实施；
  验收含静态检查、单元/集成、运行时与端到端多层证据，并含跨档案缓存泄漏等
  负向用例。
- **原则二（三层身份隔离）**：FR-016/020/021/022 将 Household/Account/Profile
  隔离延伸到前端缓存层；身份切换清缓存、过期响应丢弃为强制验收项。
- **原则三（公开浏览与受控播放）**：公共/个人缓存分域不改变"公开可浏览不代表
  可播放"；播放鉴权仍由服务端裁决，前端缓存不缓存任何播放凭据。
- **原则五（ADR 与非破坏性演进）**：统一数据层与 hooks 库选型属重大技术选型，
  实施前必须新增 ADR；遗留 `lib/api.ts` 的退役在 ADR 中显式记录替代关系。
- **技术约束 3（幂等与一致性）**：FR-013/014 保持变更幂等与服务端契约不变。
- **技术约束 4（领域解耦）**：FR-043 保证查询库与组件库依赖不进入领域核心。
- **技术约束 5（HeroUI 优先，v1.3.0）**：FR-001/002/004 为其直接落实。
