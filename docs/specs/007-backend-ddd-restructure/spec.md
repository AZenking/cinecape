# Feature Specification: 后端代码结构宪章对齐调整（DDD 分层 + nestjs-best-practices 全量合规，零遗留）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 后端源码全量按分层落位、依赖方向向内 (Priority: P1)

后端维护者打开后端代码库时，每一个源码文件都能根据其所在位置直接判断出它属于哪一层职责（领域规则 / 用例编排 / 基础设施与外部适配 / 接口交付），并且任何一处代码的依赖都只指向更靠近领域核心的方向。领域核心代码中不存在对具体呈现框架、网络传输方式或存储实现细节的引用。

**Why this priority**: 这是宪章 v1.4.0 技术约束第 6 条的直接要求，是其余边界与合规工作的结构基础；没有分层落位，边界收口与规则合规无从判定。

**Independent Test**: 对后端源码运行一次分层归属与依赖方向的自动化审计，输出零越界结论，即视为本故事可独立交付价值。

**Acceptance Scenarios**:

1. **Given** 后端全部源码文件，**When** 执行分层归属审计，**Then** 每个文件均归属唯一分层，不存在无法判定归属的文件。
2. **Given** 全部代码依赖关系，**When** 执行依赖方向审计，**Then** 不存在任何外层（接口/基础设施）被领域核心反向依赖的路径。
3. **Given** 领域核心源码，**When** 检索对具体框架装饰器、传输细节与存储驱动标识的引用，**Then** 结果为零。

### User Story 2 - 限界上下文边界收口，行为零变化 (Priority: P1)

各业务上下文（身份与账号、档案与策略、媒体目录、EPG、直播、播放、个人数据、设置、来源等）之间的协作只能通过显式发布的接口、领域事件或共享契约进行。任何"顺手直接读邻居的表""绕过规则层改数据"的路径被消除。整个调整过程中，系统的外部可观察行为保持完全不变：既有调用方拿到的响应、错误语义与数据兼容性与调整前一致。

**Why this priority**: 边界收口是"不得越界"的宪章要求核心；行为零变化保证这次调整对用户与既有集成零风险，两者共同构成本规格的安全底线。

**Independent Test**: 对全部跨上下文引用做静态审计并对照行为回归证据（同一请求调整前后响应一致、既有测试全部通过），即可独立验收。

**Acceptance Scenarios**:

1. **Given** 全部跨上下文代码引用，**When** 执行边界审计，**Then** 每一处引用都指向显式发布接口、领域事件或共享契约，零处直取内部存储结构或私有实现。
2. **Given** 任一既有接口调用，**When** 在调整前后分别执行同一请求，**Then** 响应内容、状态语义与错误语义完全一致。
3. **Given** Household / Account / Profile 隔离与播放授权规则，**When** 运行既有安全边界负向测试集，**Then** 全部用例通过且未出现任何放宽。

### User Story 3 - 后端实现规则全量合规，偏离必须留痕 (Priority: P2)

后端维护者持有一份覆盖最新宪章技术约束第 7 条所指实现规则全集（40 条规则、按优先级排列）的合规清单，每一条规则在后端代码中都能给出"合规"结论，或给出指向已接受规格/ADR 的"已记录偏离"结论。清单可在合并前质量门禁中机械执行。

**Why this priority**: 宪章第 7 条要求实现层严格执行规则体系并按优先级落地；它作用于分层落位之后的代码细节，因此排在 P1 之后，但仍是本规格的强制交付物。

**Independent Test**: 逐条对照 40 条规则清单核验后端代码，输出每条规则的结论与证据位置；结论中出现无记录的偏离即不通过。

**Acceptance Scenarios**:

1. **Given** 40 条规则合规清单，**When** 对后端代码逐条核验，**Then** 每条规则均有"合规"或"已记录偏离（附规格/ADR 链接）"结论，覆盖率为 100%。
2. **Given** 任何一条无记录偏离，**When** 出现在代码中，**Then** 视为验收不通过，必须修复或补记偏离理由。
3. **Given** 规则体系与宪章冲突的场景（如规则示例所用技术与本仓库既定技术栈不同），**When** 核验结论生成，**Then** 以宪章与已接受 ADR 为准且该裁决在清单中显式记录。

### User Story 4 - 零遗留收尾与文档原子同步 (Priority: P2)

调整完成时，代码库中不存在任何"过渡状态残留"：没有迁移后遗留的孤儿文件、没有不再被引用的死代码、没有注释掉的旧实现、没有仅为绕过边界而保留的临时垫片。规格状态、ADR 与实现代码在同一次变更中保持同步，验收证据按多层证据层级留档。

**Why this priority**: "不得有任何遗留"是本规格的验收红线；它依赖前三个故事完成才能判定，因此列为收尾性 P2，但缺省即整体验收失败。

**Independent Test**: 对后端目录执行孤儿文件与死代码清点、对全库检索注释块与过渡标记、核对规格状态与 ADR 链接的同步性，全部为零/一致即通过。

**Acceptance Scenarios**:

1. **Given** 调整完成后的后端代码库，**When** 清点未被任何入口引用的源文件与导出，**Then** 计数为零。
2. **Given** 全库文本检索，**When** 查找被注释的旧实现、迁移占位标记与临时绕行垫片，**Then** 计数为零。
3. **Given** 本规格与对应 ADR，**When** 核对规格状态流转与实现提交，**Then** 状态、文档与代码在同一原子变更中同步，验收证据已按层级留档。

### Edge Cases

- 迁移脚本与应用引导入口等"非请求处理"代码：必须明确归入基础设施/入口职责并在 ADR 中记录归属结论，不得因"难以归类"而留在原地成为遗留。
- 既有横切公共工具：仅保留与分层边界一致的部分并归入正确位置；其去留结论必须逐项留痕，不得整目录原样搬运了事。
- 审计发现既有循环依赖：必须通过接口反转或事件化解，严禁以新增越界引用或复制代码的方式"打通"。
- 行为保持与边界收口冲突时（如某直连存储路径被外部依赖）：以行为零变化为底线，通过新增显式接口保持外部语义后再收口，不得改变外部契约。
- 测试代码与脚本同受边界约束：测试只能经公开入口或显式测试支持口访问被测对象，不得为测试方便而长期保留越界后门。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 后端全部源码文件必须归属唯一的结构职责层（领域规则 / 用例编排 / 基础设施与外部适配 / 接口交付），且归属关系必须可由目录结构直接判定，无需阅读实现。
- **FR-002**: 分层依赖必须单向向内；领域规则层严禁依赖任何具体界面框架、网络传输细节或存储实现细节。
- **FR-003**: 业务上下文之间的访问必须仅通过显式发布的接口、领域事件或共享契约进行；零处直取其他上下文内部存储结构或私有实现。
- **FR-004**: 必须消除绕过规则层直接读写数据的全部代码路径。
- **FR-005**: Household / Account / Profile 身份隔离与既有授权边界必须在调整全程保持，并由服务端强制，不得出现任何放宽。
- **FR-006**: 后端实现必须满足宪章 v1.4.0 技术约束第 7 条所指实现规则全集（40 条规则、按优先级）中的每一条；任何偏离必须在已接受的规格或 ADR 中记录理由与范围。
- **FR-007**: 结构调整必须保持外部可观察行为完全不变：接口契约、响应与错误语义、持久化数据兼容性均不得改变。
- **FR-008**: 交付时后端不得存在孤儿文件、死代码、被注释的旧实现或仅为过渡保留的临时垫片。
- **FR-009**: 合规结论必须可机械化核验：分层归属审计、依赖方向审计、边界审计与规则清单检查必须纳入合并前质量门禁，且结果为零违规。
- **FR-010**: 规格、ADR 与实现必须在同一原子变更中保持同步；验收证据必须按宪章原则一的多层证据层级留档（静态检查、单元/集成测试、运行时行为、真实契约）。

### Key Entities *(include if feature involves data)*

本规格不改变任何领域数据模型，既有实体（Household / Account / Profile / 内容策略 / 媒体目录 / EPG / 播放 / 个人数据等）的语义与关系保持不变。被重组的结构对象为：

- **结构职责层**：领域规则层、用例编排层、基础设施与外部适配层、接口交付层；每层有明确的允许依赖方向。
- **限界上下文**：身份与账号、档案与策略、媒体目录、EPG、直播、播放解析与交付、个人数据、设置、来源与导入等；上下文间仅经发布接口、领域事件与共享契约协作。
- **共享契约**：跨上下文与前后端复用的稳定契约集合，是被允许的跨边界引用目标之一。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 自动化分层归属与依赖方向审计报告违规数为 0，且审计可重复执行并纳入合并前门禁。
- **SC-002**: 全部既有测试（单元、集成、真实契约、安全边界负向用例）100% 通过；测试语义不变（仅允许调整导入路径类机械修改）。
- **SC-003**: 外部行为零变化：抽样覆盖全部既有接口的前后对比回归证据显示响应与错误语义完全一致，既有数据无需任何迁移即可继续使用。
- **SC-004**: 零遗留清点：未被引用的孤儿文件、死代码、注释旧实现、临时垫片计数均为 0。
- **SC-005**: 40 条规则合规清单覆盖率 100%，其中"已记录偏离"条目全部附有已接受规格或 ADR 链接。
- **SC-006**: 文档同步完成：规格状态流转、新增 ADR 与实现出现在同一原子变更中，验收证据留档可追溯。

## Assumptions

- 本次为纯结构对齐调整：不改变任何对外接口契约、不改变数据库结构与既有数据、不触碰规格 005 / 存储代际 2 的既定交付例外。
- 数据持久化迁移脚本与应用引导入口按基础设施与入口职责归置，归属结论在 ADR 中显式记录。
- 既有横切公共工具逐项判定去留与归属，不整目录机械搬运。
- 实施前必须先产出并接受记录结构方案、迁移映射与规则偏离清单的 ADR（宪章原则五）。
- 规则体系与本仓库技术栈冲突之处以宪章与 ADR 为准，该裁决方式写入合规清单使用说明。
- 测试与辅助脚本随所属层归位并受同一边界约束。

## 宪法合规评估

- 对应宪章 v1.4.0 技术约束第 6 条（后端 DDD 分层与边界不可越界）与第 7 条（后端实现严格执行 `nestjs-best-practices`）：本规格即为两条约束的落地实施规格。
- 遵守核心原则一（规格先行与多层证据验收）：本规格为 Proposed 状态，未接受前不得开始实现；验收证据分层留证。
- 遵守核心原则五（ADR 与非破坏性演进）：结构方案、迁移映射与规则偏离清单必须先经 ADR 接受；历史 ADR 不篡改，如有替代关系显式标注。
- 遵守核心原则二/三/六（身份隔离、公开浏览与受控播放、设置授权）：FR-005 明确调整全程边界不放宽，安全负向测试集必须保持全绿。
- 遵守技术约束第 3 条（幂等与数据一致性）：本次不涉及接口语义与数据结构变更，既有幂等与迁移要求继续有效。
- 与技术约束第 4 条（领域核心解耦）关系：FR-002 为其在后端的强化落地，无冲突。
