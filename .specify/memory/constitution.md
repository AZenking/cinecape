# Home Media Platform 宪章 (Constitution)

## 核心原则 (Core Principles)

### 一、规格驱动与多层证据验收（不可妥协）
所有新功能、接口变更与领域模型调整，在编写实现代码之前，**必须**先编写并通过已接受的规格文档（`docs/specs/`）；涉及原则五所列重大结构设计、业务边界调整或不可逆技术选型时，还**必须**具备已接受的架构决策记录（`docs/adr/`）。不涉及上述决策的变更可不新增 ADR，但仍**必须**遵循适用的已接受 ADR，不得借此豁免规格或验收要求。代码实现规格，自动化与手工测试证明规格。处于 `Proposed` 状态的未接受规格**严禁**作为实现承诺。所有验收标准必须具备客观可判定的二元结果，并且必须在明确的证据层级中提供证明：静态检查、单元/集成测试、运行时行为以及网络/后端契约。仅通过单元测试**绝不能**替代运行时或真实契约证据。任何涉及权限、状态变更或数据修改的规格，**必须**显式包含越权访问、非法入参与防篡改的负向验收条件。

### 二、三层身份与数据边界严格隔离（Household / Account / Profile）
所有业务逻辑、存储结构与 API 契约，**必须**严格遵循 `Household -> Account -> Profile` 三层层级结构：
1. **Household**（家庭）是顶层资源边界（`household_id`）。所有媒体源、媒体库、物理设备和家庭级策略均归属于 Household。
2. **Account**（账号）仅负责认证、凭据校验、设备会话及管理员权限。V1 阶段单个 Household 由一个主 Account 管理；Account 不得混淆为观看者个体。
3. **Profile**（档案/画像，`profile_id`）代表当前观看者。观看历史、播放进度、收藏夹、待播清单（Watchlist）及个性化偏好**必须**直接绑定至 `profile_id`。个人数据**绝不允许**与 `account_id` 耦合，更**严禁**跨 Profile 泄漏。

游客响应**不得**返回任何 Profile 的个人收藏、观看历史、播放进度或其他个人数据。
个人数据的查询、写入与缓存**必须**保留 Household 和 Profile 隔离；服务端**必须**校验
有效会话及经验证的目标 Profile 归属，不得仅信任客户端提交的档案标识。
切换 Profile 或退出登录时，客户端**必须**清除不再属于当前身份的个人数据展示与缓存，
并阻止旧在途响应回写；公共响应与公共缓存**不得**混入个人数据。

「主 Profile」可以作为设置入口与 PIN 验证目标，但**不得**仅凭默认档案标识、成人类型
或主档案标识获得管理员权限。管理员权限仍由 Account 承担，并由服务端验证；
Profile 的观看身份与个人数据归属职责不变。

### 三、公开浏览与默认安全的服务端播放鉴权（Public Browsing & Secure Playback Authorization）
公开内容元数据的浏览与播放资源访问**必须**分离。除管理设置及个人数据访问外，
内容页面浏览**不得**以登录或选择 Profile 为前提；游客可以浏览当前部署实例所属
Household 的全部可用内容元数据，包括媒体目录、详情、直播节目和 EPG 节目单。
游客浏览**不得**要求 ProfilePolicy 放行；资源归属与可用性仍**必须**由服务端校验。
V1 的匿名浏览家庭上下文**必须**由单部署单 Household 的服务端配置或数据确定，
不得由匿名客户端指定。公开浏览**不得**授予播放权限，也**不得**暴露源地址、
物理路径、来源凭据、播放票据或可直接获取媒体流的地址。

播放解析器（`Playback Resolver`）是直播频道（Live TV）、电影、电视剧集与 NAS 本地文件获取播放资源的唯一统一入口。客户端上报参数、本地存储标记（`localStorage`）及 URL 参数**绝不可**作为授权信任源。服务端**必须**基于经过验证的设备会话（`DeviceSession`）解析并校验绑定的 `activeProfileId`。播放资源访问授权**必须**通过内容策略（`ProfilePolicy`，包含内容分级、媒体黑白名单、未分级策略及频道白名单）进行动态计算，不得仅依赖前端展示性的档案模式（如 `adult/child`）。只有当设备会话有效、Profile 归属当前 Household、内容策略放行、家庭拥有该资源且设备能力匹配时，播放资源方可解析并下发。

播放解析、票据签发、媒体流及字幕等播放资产交付**必须**保持受控授权，**严禁**因开放
浏览而允许匿名播放或绕过当前 Profile 的播放权限。公开可浏览不代表当前 Profile 可播放。

### 四、自托管 NAS 与隐私优先架构（Self-Hosted & Privacy-First）
平台专为家庭及个人 NAS 运行环境设计，数据自主可控与本地化是核心基石。在 V1 阶段，单个部署实例严格对应单个 Household（遵循 ADR-0002）；但所有数据库表结构、缓存键与存储路径**必须**保留显式的 `household_id` 边界，确保未来演进时不发生结构性重构。用户个人观影记录与媒体元数据**必须**保存在本地私有基础设施中，核心流媒体与播放功能**严禁**引入任何强制性外部云端依赖或非授权遥测。

### 五、架构决策记录（ADR）与非破坏性演进
所有重大结构设计、业务边界调整及不可逆的技术选型，**必须**沉淀于受版本控制的架构决策记录（`docs/adr/`）。当技术或业务需求发生重大演变时，历史 ADR **严禁**被静默篡改或删除；旧决策必须通过新增 ADR 进行形式化废弃（标记为 `Superseded`），并附带清晰的迁移路径与背景分析。规格文档、ADR、代码实现和测试套件**必须**在同一次原子变更中保持完全同步。

### 六、管理设置的角色差异化与分级授权生命周期
设置系统**必须**严格遵循角色差异化（Role-Differentiated）与纵深防御原则，
授权事实**必须**由服务端单一真实源判定，前端入口与路由状态仅作为交互呈现，不得作为安全信任源。

1. **角色差异化与菜单纯粹隔离**：
   - 普通观看者 Profile 进入设置仅呈现【个人偏好】（播放体验、界面外观、我的档案）；家庭管理与系统安全模块在侧栏及 DOM 中**彻底不渲染**，并辅以路由守卫拦截，避免误操作与门禁打扰；
   - 主管理员 Profile 呈现全量个人偏好、家庭资源与系统安全模块。
2. **免套娃授权与常规管理通行（依据已生效 ADR-0017）**：
   - 全局身份切换收敛于右上角身份菜单。通过标准 PIN 选档验证激活主管理员身份（`session.activeProfile.isMain === true`）后，常规管理设置（来源、EPG、分级策略、家庭时区等）直接畅行，**严禁**重复弹出二次设置 PIN 或施加临时 Ticket 倒计时阻断（废除原 15 分钟临时 Ticket 机制）；
   - 服务端（`SettingsGuard`）**必须**强校验当前有效会话关联的主管理员身份与 Household 归属，非主管理员请求直接 403 阻断。
3. **高危不可逆操作的底线防御（保留 ADR-0006）**：
   - 常规管理畅行**绝不得**替代不可逆破坏性操作的二次验证底线。修改主账号密码、注销关键档案或清空家庭资源等高危操作，**必须**显式弹出单次主账号密码验证，随当次业务请求原子提交服务端校验，**严禁**长期缓存敏感授权凭据。
4. **失效边界**：退出登录、会话撤销、切换为非主管理员 Profile、档案停用或账号密码变更时，主管理员特权**必须**即时彻底失效。

### 七、频道中心制与物理源/EPG源彻底解耦原则 (Channel-Centric Logical Abstraction)
系统对直播媒体资产的管理、组织与呈现，**必须**严格遵循以逻辑频道（Logical Channel）为核心的设计范式，将上层业务视图与底层物理数据源彻底解耦：

1. **逻辑频道是客户端唯一交互与鉴权实体**：
   - 客户端（页面频道列表、EPG 电子节目指南、时钟进度条、搜索及播放器）呈现、浏览与请求播放的唯一实体对象**必须且只能**是「逻辑频道」（统一由 Catalog `MediaItem`，`type='channel'` 承担）；
   - 系统**严禁**将物理直播源（IPTV 订阅源）或原始流地址作为独立业务实体直接暴露给普通用户或作为页面消费主体。
2. **多直播源汇聚为频道的物理播放线路（1:N Playback Lines）**：
   - 多个外部直播源（M3U 等）在系统内仅作为物理传输层（Transport Layer）的数据供给；导入或同步后，同名或同标识的物理流**必须**自动汇聚归集至对应逻辑频道的播放线路集合（`Playback Lines`，如高清、标清、备用线路、IPv6 等）；
   - 播放解析器（`Playback Resolver`）统一向播放器下发该逻辑频道的可用线路列表，由播放器在频道上下文内实现多线路无缝切换与自动故障转移（Failover），上层业务与页面视图无感知底层物理源的具体提供方。
3. **多 EPG 源的聚合供给与确定性级联归一（Multi-EPG Aggregation & Cascading Resolution）**：
   - 多个 EPG 来源（XMLTV）在系统内构成家庭统一的节目排期元数据池，为逻辑频道提供时序节目单支持；
   - 逻辑频道与 EPG 节目单的匹配**必须**严格遵循确定性的级联优先级（单频道手动绑定锁定 > 精确 tvg-id 匹配 > 源优先级权重级联 > 频道别名智能归一匹配 > 兜底降级「暂无节目单」），**严禁**建立物理直播源与单一 EPG 源之间 1:1 的强绑定或以此扭曲频道的元数据消费。
4. **管理后台的频道资产工作台纯粹性（Channel-Centric Administration）**：
   - 管理设置后台**必须**以逻辑频道为中心组织工作流，提供频道线路查看/调整与跨源 EPG 绑定修正工作台；**严禁**设计诱导或混淆用户认知的“源与源直接对齐（Source-to-Source Matching）”界面。

## 技术约束与环境规范

1. **目标运行环境**：基于 Docker/Linux 容器化交付，适配主流家用 NAS 硬件平台，保持轻量高效的 CPU 与内存占用。
2. **媒体与流式处理**：支持 NAS 本地文件系统直接挂载与标准化流协议（如 Direct Stream、HLS/DASH）。转码能力与媒体解析需与核心业务事务有效解耦。
3. **幂等性与数据一致性**：播放进度上报、观看状态更新与收藏夹操作等状态变更接口**必须**具备幂等性保证。数据库迁移默认**必须**支持向前兼容，并包含经测试验证的回滚方案。历史业务数据迁移与保留的豁免**仅允许**适用下文宪章明文列出的特定交付例外；ADR、实施计划或代码不得自行增加豁免范围。
4. **领域核心解耦**：核心领域模型与业务规则**不得**反向依赖任何特定前端框架、UI 呈现方式或具体网络传输协议。
5. **PC 端 UI 组件规范（HeroUI v3 优先，禁用原生组件）**：PC 端界面组件**必须**基于 HeroUI v3（`@heroui/react`、`@heroui/styles`）实现，**严禁**混用 HeroUI v2 的 API、Provider 或主题模式。可交互组件（按钮、输入框、下拉与选择器、日期/时间选择、文件选择、模态框与对话框、提示与确认、表格、标签页、菜单、导航、加载与进度指示等）**严禁**使用浏览器原生控件替代（原生 `<select>`、`<datalist>`、`<input type="date|time|file">`、`<dialog>`、`<progress>`/`<meter>` 及 `alert()`/`confirm()`/`prompt()` 等）。「尽可能使用 HeroUI」**必须**落实为：组件需求一律先采用 HeroUI 现有组件；仅在 HeroUI 确实未覆盖所需能力时，才允许以与 HeroUI 设计体系一致的自定义或无头组件实现，且偏离原因**必须**记录于对应功能规格或 ADR 中，**严禁**以省事为由回退原生控件。本条禁止的是业务呈现代码直接以原生控件替代组件；HeroUI 或合规自定义/无头组件内部为语义、可访问性、表单提交或浏览器能力而生成或封装的原生 HTML 元素不在禁令内，但不得借封装之名绕过 HeroUI 优先、偏离记录或既有安全要求。本约束仅作用于 PC 端呈现层；核心领域模型与业务规则仍遵循第 4 条，**不得**反向依赖 HeroUI 或任何具体 UI 框架。
6. **后端架构：DDD 分层与边界不可越界**：后端（`apps/server` 及未来后端服务）架构**必须**采用领域驱动设计（DDD）分层——领域层（实体、值对象、领域服务、领域事件与业务规则）、应用层（用例编排与事务边界）、基础设施层（Drizzle/SQLite、文件系统、外部媒体源等适配器）与接口层（NestJS Controller、DTO 与传输契约）。依赖方向**必须**向内：接口层 → 应用层 → 领域层；领域核心**严禁**依赖 NestJS 装饰器、HTTP 传输细节、具体 ORM 或任何框架 API（本条是第 4 条在后端的展开与强化）。模块**必须**按限界上下文/功能划分；跨上下文访问**只能**通过显式发布的接口、领域事件或共享契约包（`@hmp/shared`）进行，**严禁**直取其他上下文的内部表结构、私有服务，或由接口层、跨上下文调用方直接读写数据库。应用层**可以**通过本上下文显式定义的仓储或查询端口访问基础设施适配器；纯读取用例可通过查询端口返回只读投影，无须为查询强制构造领域实体。该路径仍**必须**执行服务端授权、Household/Profile 隔离及适用的内容策略，且不得泄漏内部表结构或绕过领域业务规则；状态变更**必须**由应用层编排并执行领域规则及事务边界。`Household/Account/Profile` 等既有边界**必须**由服务端类型与领域规则强制，不得仅依赖目录约定或客户端自律。任何跨层直调、旁路直连或边界合并，**必须**先经已接受的 ADR 论证，否则视为违宪缺陷。
7. **后端实现：严格执行 `nestjs-best-practices`**：后端 NestJS 代码的编写、审查与重构**必须**严格执行 `nestjs-best-practices` skill 的 **1.2.0 固定版本**（40 条规则、10 类别），并按其优先级落地：架构与依赖注入（CRITICAL）优先，其后为错误处理、安全、性能（HIGH），测试与数据库（MEDIUM-HIGH），API 设计、微服务与 DevOps。至少**必须**落实：功能模块组织与循环依赖禁止、构造器注入与注入令牌、统一异常过滤器与 HTTP 异常、DTO 输入验证与 Guards/限流、查询与事务优化（含 N+1 防护）、DTO 序列化、`@nestjs/testing` 单元测试与 Supertest 契约测试、ConfigModule 配置、结构化日志与优雅停机。skill 与本宪章或仓库既定技术栈冲突时（如 skill 示例使用 TypeORM 而本仓库为 Drizzle），**以宪章与已接受的 ADR 为准**；skill 中与技术栈无关的模式（仓储抽象、事务边界、测试策略等）仍**必须**执行。该固定版本的 `SKILL.md` 及其引用规则文件共同构成核验基线，全局安装版本更新不得自动改变本宪章的要求。后端 Pull Request **必须**注明实际使用的 skill 版本及可复核的规则来源；版本不符时**必须**取得并按 1.2.0 基线核验，不得以最新版本默默替代。升级基线**必须**通过宪章修订记录版本差异及影响。后端 Pull Request **必须**对照该固定版本 skill 与本宪章进行合规核验；有意偏离**必须**有经接受的规格或 ADR 记录理由。


8. **前端 UI 实现与设计规范（HeroUI skill、DESIGN.md 与语义 token）**：PC 端 UI 的设计、编写、审查与重构**必须**严格执行 `heroui-react` skill 的 **3.0.1 固定版本**及其引用文档获取流程；实现前**必须**读取所用组件和主题的官方 v3 文档，并核对项目实际安装版本，禁止凭 v2 经验推断 v3 API。skill 的 `SKILL.md` 及其引用规则共同构成核验基线；UI Pull Request **必须**记录实际 skill 版本、可复核来源和所依据的组件/主题文档版本或获取日期。全局 skill 更新不得自动改变基线，升级基线**必须**经宪章修订并记录影响。
   - **统一实施指令**："Build this interface with HeroUI v3. Follow DESIGN.md for visual decisions and use semantic HeroUI tokens instead of hardcoded values."
   - **视觉决策来源**：仓库根目录 `DESIGN.md` **必须**作为 PC UI 的视觉规范入口，采用官方默认主题设计契约，约束布局、字体层级、色彩语义、间距、圆角、交互状态、响应式与主题决策，并与对应已接受规格保持一致。项目特定的补充决策**必须**在该入口中记录或显式链接；官方契约与实际安装包不一致时，组件 API 与 token 定义以安装版本及其主题 CSS 为准，并记录和修正差异，不得默默硬编码替代。若该文件缺失或未覆盖实施所需决策，**必须**在相应 UI 实施前补齐并按规格流程确认，不得在组件中自行发明一套视觉规则。`DESIGN.md` 服从本宪章与已接受 ADR，不得修改授权、身份隔离或其他安全边界。

## 开发工作流与质量门禁

1. **工作流全生命周期**：遵循 `项目简报 (Project Brief) -> 领域模型 (Domain Model) -> 功能规格 (Feature Spec) -> 架构决策 (ADR, 必要时) -> 编码实现 -> 多层证据验收 -> 发布归档`。
2. **规格状态流转**：规格必须按序显式流转：`Proposed -> Accepted -> Implementing -> Verified`（或 `Superseded`）。
3. **合并前质量门禁**：
   - 静态类型检查与代码规范检查通过，无阻断警告或错误；
   - 单元测试与集成契约测试 100% 通过；
   - 包含越权、跨 Profile 篡改、未授权内容拦截等安全边界负向测试用例且通过；
   - 涉及公开浏览的变更必须证明游客可读取全部可用内容元数据、无法匿名播放，
     且公共响应不含个人数据、源位置或播放凭据；
   - 涉及个人数据或设置访问的变更必须证明跨 Profile 请求与旧响应回写被隔离，
     未解锁设置访问及失效授权被拒绝；
   - 伴随代码的文档、规格状态与 ADR 更新必须在同一代码变更中提交。

## 治理与演进规则 (Governance)

1. **宪章最高效力**：本宪章是 Home Media Platform 的最高工程与架构治理准则，效力高于任何口头约定、未书面化的团队习惯或临时的代码审查让步。
2. **修订流程**：任何对核心原则的修改均需提出正式修订提案，详述修订原因、影响评估及迁移方案，并由核心维护者一致通过方可生效。

4. **语义化版本定义**：
   - **MAJOR（主版本）**：对核心治理原则的向后不兼容变更、治理结构重大重组或核心边界定义废弃。

### 1.10.0 修订记录（2026-11-09）

- **授权与原因**：维护者在本次讨论中明确提出，页面与用户最终消费的应是逻辑频道本身，而非具体某一个物理直播源或孤立的 EPG 源；既有界面与概念中存在的“直播来源与 EPG 来源 1:1 关联”逻辑怪异且违背实际多源聚合场景。为彻底确立以逻辑频道为中心的领域模型与用户体验，特在宪章中新增核心原则七。
- **版本依据**：新增独立的第七项核心原则（频道中心制与物理源/EPG源彻底解耦原则），现有核心原则一至六及技术约束保持完好并获得继承，按 MINOR 从 1.9.0 升至 1.10.0。
- **影响评估**：
  1. 页面消费层（`apps/web`）仅面向逻辑频道（`MediaItem`）获取节目指南、当前时钟、播放线路，播放器切线与 Failover 均在逻辑频道内自洽闭环；
  2. 废弃并重构设置中心将直播源与 EPG 源 1:1 强绑定的旧逻辑与残余界面，全面转向以“逻辑频道资产工作台”管理线路聚合与多 EPG 智能级联匹配；
  3. 后端服务保持 DDD 分层与领域模型纯洁性，`MediaItem` 实体持有 `lines` 属性，EPG 服务在频道上下文按级联算法解析节目单。
- **边界**：本原则不破坏三层身份隔离（原则二）与受控播放鉴权（原则三），所有频道播放解析仍须受 `ProfilePolicy` 严格管制；公开浏览仍只下发频道与节目元数据，不泄漏物理流凭据。
